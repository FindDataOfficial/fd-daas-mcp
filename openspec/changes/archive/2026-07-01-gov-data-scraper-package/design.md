## Context

`mcp/scrapling-uv-mcp/scripts/` holds 11 self-describing scrapers for Chinese central-government ministry open-information archives (MOF, PBC, NDRC, MOFCOM, MOHURD, MOT, MOA, SAFE, MNR, MEE, MEM). Each script carries a module-level `MANIFEST = ScrawManifest(...)` (defined in `scraw_contract.py`) declaring: identity (`name`, `label`, `url`, `description`), category, an output record schema (`columns: list[ScrawColumn]`), the sub-archives it crawls (`archives`), and free-form crawl params (`crawl`). `register.py` consumes those manifests to write the monorepo's `mcp/daas.db` (`sources` + `datasource_columns` + `scraw_configs`).

The scripts are coupled to the monorepo: `scraw_contract.to_config()` hardcodes `mcp/scrapling-uv-mcp/scripts/...` paths, `register.py` walks up the tree to find `mcp/daas.db`, and the only way to discover the registered schema is the `dashboard-mcp` or raw `daas.db` SQL. None of this is shareable as a unit.

The user wants a standalone GitHub Python project: the crawlers + the datasource/column registry, usable without the monorepo or MCP.

## Goals / Non-Goals

**Goals:**
- One pip-installable package (`gov-scraw`) containing all 11 scrapers, importable + CLI-runnable.
- A self-contained registry (SQLite + JSON) of the 11 datasources and their column schemas, generated from the `MANIFEST`s, queryable via a small read API and a CLI.
- Decoupled: no import of `mcp/`, `mcp/models`, or `scrapling-uv-mcp`; vendors its own `scraw_contract`.
- GitHub-ready: README with per-ministry table + usage, LICENSE, .gitignore.
- The monorepo's original scripts stay bit-for-bit unchanged.

**Non-Goals:**
- Replacing the monorepo scripts with re-exports from this package.
- PyPI publication (install is `pip install git+https://...`).
- MCP server, cron integration, or detail-page body crawling.
- Crawl scheduling / incremental cursoring.
- Bilingual i18n of the README beyond what the MANIFESTs already carry.

## Decisions

### Decision: Copy, don't move; vendor `scraw_contract`
The package copies the 11 scripts and a trimmed `scraw_contract.py` into `gov_scraw/`. The monorepo originals are untouched.
- *Why*: zero risk to the working monorepo + MCP registration flow; the package is a separate distribution channel. Moving would force a cross-cutting refactor of `register.py`, `daas.db`, and the `cn-ministry-scraw-sources` spec for no shareability gain.
- *Alternative*: make `mcp/scrapling-uv-mcp/scripts/` import from the package. Rejected — couples monorepo to a new package's release cadence and is explicitly out of scope.

### Decision: Registry is a *derived* artifact, the `MANIFEST` is the source of truth
`registry.db` + `registry.json` are generated by `gov-scraw build-registry`, which imports each script's `MANIFEST` and writes `sources` / `datasource_columns` / `scraw_configs` rows using the same translation logic as the monorepo's `register.py`. The generated files are checked in so consumers get them without running the build.
- *Why*: the manifest is already the canonical schema description; duplicating it by hand into a DB would drift. Reusing the exact `to_columns_json()` / `to_scraw_columns()` translation keeps the package's registry byte-equivalent in shape to the monorepo's `daas.db` rows for these 11 sources.
- *Alternative*: ship a frozen JSON only (no SQLite). Rejected — the user explicitly wants "datasource and data structure defined in it" queryable like `daas.db`; a SQLite file mirrors the daas experience and supports the read API with zero parser code (sqlalchemy).

### Decision: SQLite schema is a *subset* of daas, standalone (no `mcp/models` dependency)
The bundled `registry.db` has three tables — `sources`, `datasource_columns`, `scraw_configs` — with the same column shapes as `daas.db` for those tables, but created by the package's own `build_registry.py` via raw `sqlite3`/`sqlalchemy`. No FK to the legacy `datasources` table (the stale-FK gotcha the monorepo's `register.py` works around with `PRAGMA foreign_keys=OFF`).
- *Why*: consumers don't need `combine-mcp`'s `datasources` table or the other 13 daas tables; they need the 11 sources and their columns. Dropping the stale FK removes a footgun.
- *Alternative*: copy `mcp/daas.db` wholesale. Rejected — drags in unrelated MCP registration, `observations`, `process_rules`, etc., and a 11-row consumer shouldn't inherit a multi-MCP schema.

### Decision: Read API + CLI are thin wrappers over the bundled DB
`gov_scraw.list_sources()`, `.get_source(name)`, `.get_columns(name)` open the bundled `registry.db` read-only and return dataclasses/dicts. The `gov-scraw` CLI has three subcommands: `crawl <name>` (delegates to the script's `main()`), `list` (prints sources), `describe <name>` (prints source + columns).
- *Why*: stdlib `argparse` + `sqlite3` covers it; no Click/FastMCP needed. The crawl path reuses each script's existing `main()` so crawl behavior is identical to the monorepo.
- *Alternative*: expose as an MCP server. Rejected — the user asked for a Python project to share on GitHub, not another MCP.

### Decision: Crawl entry point resolves scripts by import, not subprocess
`gov-scraw crawl <name>` imports `gov_scraw.scripts.<name>` and calls its `main()` with a synthesized `sys.argv`. The scripts are copied with their `from scraw_contract import ...` rewritten to `from gov_scraw.scraw_contract import ...` (a one-line sed at copy time, recorded in the build).
- *Why*: subprocess + `uv run --directory` is monorepo-shaped; a pure-Python import is what a pip-installed package user expects.
- *Trade-off*: the copied scripts keep their module-level `Fetcher` import and `argparse` `main()`, so they remain independently runnable too.

## Risks / Trade-offs

- [Drift between monorepo scripts and package copies] → The package is a snapshot. Mitigation: `build-registry` imports the *package's* copies, so the registry always matches the shipped scripts; a CHANGELOG note states the snapshot date. A future change can add a sync script.
- [Ministry sites change their markup] → same risk as the monorepo; not introduced by this change. Mitigation: none beyond what exists; the README documents the "catalog crawl" nature and per-script `--max-pages` cap.
- [Bundled `registry.db` goes stale vs. the `MANIFEST`s in the same checkout] → Mitigation: `build-registry` is logically idempotent (re-running produces an identical `.dump` and byte-identical `registry.json`; only SQLite's file-change-counter header byte differs, which is unavoidable on any write). The CI/test step re-runs it and `git diff --exit-code` asserts the checked-in `registry.json` matches; a failing diff tells the maintainer to commit the regeneration.
- [Crawling `.gov.cn` from a pip-install] → polite pacing (`SLEEP = 0.3`) is preserved verbatim from the scripts; the README restates "do not hammer, use `--max-pages`".
- [`scraw_contract.to_config()` hardcodes monorepo script paths] → The package vendors a trimmed `scraw_contract` whose `to_config()` omits the `scraper_script`/`scraper_script_docker` monorepo-path fields (they're meaningless outside the monorepo). `to_columns_json()` and `to_scraw_columns()` — the parts `build-registry` actually uses — are kept identical so the registry rows match.
