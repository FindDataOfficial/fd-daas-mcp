summary: |
  Replace the akshare-agent-harness JSON registry with a SQLAlchemy-backed
  database (default SQLite, swappable to PostgreSQL/MySQL). Store all function
  metadata — command name, datasource (category + API source), description,
  parameters, and output columns — in a normalized two-table schema. Write a
  migration script to populate from the existing registry.json. Update the
  registry.py module to query the DB instead of parsing JSON.
changes_made:
  - Scope expanded from "4-field SQLite" to full JSON replacement — the user wants SQLAlchemy as single source of truth, not a supplementary store
  - Datasource clarified: both `category` (domain like 历史行情) and `source` (API provider like 东方财富) are stored, not just one
  - Schema normalized: columns stored in a separate 1:N table instead of JSON blob, for queryability
  - Database layer uses SQLAlchemy ORM so the backend is swappable (SQLite → PostgreSQL/MySQL) via config URL
  - Migration approach: write a one-shot import script from existing registry.json, not change the upstream generation pipeline
  - Parameters stored as JSON column (variable-length list doesn't justify a third normalized table)
steps_refined:
  - "1. Create SQLAlchemy models (core/models.py): Function model (id, command, category, source, description, parameters/JSON) + FunctionColumn model (id, function_id/FK, column_name, column_type, column_description)"
  - "2. Create database module (core/database.py): engine/session factory, configurable DATABASE_URL env var, default to SQLite at metadata/registry.db, auto-create tables"
  - "3. Write migration script (scripts/migrate_registry.py): read existing registry.json, upsert into SQLAlchemy DB, verify row counts match"
  - "4. Update core/registry.py: replace json.load/_load_registry with SQLAlchemy session queries (list_functions, search_functions, get_function_info, get_categories, get_category_functions)"
  - "5. Update runner.py (if needed): ensure call_akshare_function still works with DB-backed registry"
  - "6. Update tests: add SQLite in-memory DB fixture, update test_core.py, verify test_full_e2e.py still passes"
open_questions:
  - Should the migration script be idempotent (delete-and-recreate) or upsert (merge new functions, keep existing ones)?
  - Should we keep registry.json as a fallback if the DB is missing, or fail fast?
  - Should the DB file be committed to git, or treated as a build artifact (generated by migration)?
notes: |
  The user wants SQLAlchemy for future flexibility — today it's SQLite in this project,
  tomorrow it could be PostgreSQL for a shared service. The design should treat the DB
  URL as the only config surface. Parameters are stored as JSON because they vary
  per function and are rarely queried directly (unlike columns, which justify their own table).
  The registry.py API surface (list, search, info, categories) must remain backward-compatible
  — callers should not need to know the storage changed.
