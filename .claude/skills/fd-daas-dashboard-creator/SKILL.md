# fd-daas-dashboard-creator

Build a standalone HTML dashboard for daas data. Each dashboard is one self-contained HTML file at `dashboards/<slug>.html` (repo-root `dashboards/`, configurable via `DASHBOARDS_DIR`), rendered with **ECharts** (vendored locally) and carrying interactive **entity + time-range filters**. Every dashboard's metadata is registered in the `dashboards` table in `daas.db` via `scripts/register_dashboard.py register`; that call also regenerates `dashboards/index.html` + `daas.md` from the DB, so the charts index can never drift from the registry.

## daas.db location

`DAAS_DATABASE_URL` in the repo-root `.env` points at the DB (currently `sqlite:///daas.db`). From the repo root, `sqlite3 daas.db "..."` works.

## Mental model

Seven steps, with two gates before any state mutates:

1. **Propose structure** - name, introduction, charts, entity scope, time range, refresh cadence.
2. **Permission gate** - ask before doing anything.
3. **Validate source data** - `sqlite3` fetch + confirm coverage before baking. Gate: shortfalls surface (skip/widen/abort); empty aborts.
4. **Build** - write `dashboards/<slug>.html` with ECharts + entity/time filters + validated data baked as JSON.
5. **Open** - offer to open in the browser.
6. **Iterate then register** - change loop -> accept -> `scripts/register_dashboard.py register` (writes the DB row + regenerates `index.html`/`daas.md`).
7. **Write instruction md** - companion `<slug>-dashboard.md` under `daas-doc/`.

Never write files or mutate state before step 2's permission. Never bake data before step 3's validation passes.

## Step 1 - Propose the structure

1. Read the data shape via `sqlite3`:
   ```bash
   sqlite3 daas.db "SELECT * FROM <scraw_slug or observations> LIMIT 20"
   sqlite3 daas.db "SELECT name, source_table, value_column, op FROM indicator_rules WHERE name LIKE '%<term>%'"
   ```
2. Draft the structure as markdown: **Name** (human-readable), **Introduction** (one paragraph), **Charts** (ECharts type + source table + columns + x-axis + filter fields), **Tables**, **Entity scope**, **Time range**, **Refresh cadence** (static snapshot vs manual - there is no cron).
3. Show the draft and ask: "Does this look right? I'll validate the data and build once you confirm."

## Step 2 - Permission gate

Do NOT write any file, bake any data, or mutate state until the user accepts. If they request changes, revise and re-ask. If they decline, stop.

## Step 3 - Validate the source data

1. Fetch the rows you'll chart via `sqlite3` (limit high enough to cover the time range):
   ```bash
   sqlite3 daas.db "SELECT * FROM <source_table> WHERE <date> BETWEEN '<start>' AND '<end>' LIMIT 1000"
   ```
2. Check: columns exist, every entity in scope has rows, rows fall in the time range, non-zero count.
3. Surface a **coverage summary**: "Fetched N rows over D1-D2 for entities X, Y (M of K requested). Columns: ..."
4. **On shortfall**: do NOT bake partial data silently. Tell the user what's missing and ask skip/widen/abort.
5. **On empty**: abort with a message naming the source table + filter; do not write HTML.

## Step 4 - Build the standalone HTML

1. **Slug**: kebab-case from the name (e.g. "比亚迪日行情 + 5日均线" -> `byd-daily-sma5`). Must match `^[A-Za-z0-9_-]+$`.
2. **ECharts vendored locally** at `dashboards/vendor/echarts.min.js`, loaded via relative `<script src="vendor/echarts.min.js">` - NOT a CDN (silent failure behind proxies). If missing, fetch once: `curl -fsSL https://cdn.jsdelivr.net/npm/echarts@5/dist/echarts.min.js -o dashboards/vendor/echarts.min.js`. If offline, tell the user to download it manually and stop.
3. **First-run scaffolding**: if `dashboards/` doesn't exist, create it (and `vendor/`). `index.html`/`daas.md` are regenerated by Step 6's `register_dashboard.py`.
4. **Bake the validated data** as `<script id="dashboard-data" type="application/json">…</script>`, keyed for entity+date slicing.
5. **Write the HTML** (use `references/template.html` as a starting point) with: the vendored ECharts script, the baked JSON, an entity `<select>` filter, a time-range start/end `<input>` filter, and a `<script>` that on any filter change slices the JSON and calls `chart.setOption` on every chart - no page reload.
6. Report the file path + `file://` URL.

## Step 5 - Open in the default browser (question 1 of 2)

Offer to open. On macOS: `open <url>`. **Ask permission first.** Accept -> launch + confirm. Decline -> print URL. Either way, proceed to Step 6. Ask ONLY the open question here - do NOT bundle the registration question (Step 6) into the same prompt; the user should look at the dashboard before deciding to register.

## Step 6 - Iterate then register (question 2 of 2)

1. Ask (own prompt): register now, or make changes first.
2. **Changes**: apply, re-validate if scope moved, re-write HTML, re-offer to open, re-ask. Loop until accept.
3. **Accept / register**: run `scripts/register_dashboard.py register` with the slug, name, intro, source_tables, entity_coverage, time_range, refresh_cadence, chart_config, file_path, file_url:
   ```bash
   uv run python .claude/skills/fd-daas-dashboard-creator/scripts/register_dashboard.py register \
     --slug byd-daily-sma5 --name "比亚迪日行情 + 5日均线" --intro "..." \
     --source-tables '["scraw_byd_daily","observations"]' --refresh-cadence manual \
     --file-path dashboards/byd-daily-sma5.html --file-url "file://$PWD/dashboards/byd-daily-sma5.html" \
     --entity-coverage '["600519"]' --time-range '{"start":"2024-01-01","end":"2024-12-31"}' \
     --chart-config '[{"type":"line","source_table":"scraw_byd_daily","x":"date","y":["Close","ma5"],"filterable":true}]'
   ```
   The script upserts by slug (idempotent) AND regenerates `dashboards/index.html` + `daas.md`.
4. Confirm: "Registered `<slug>`; `index.html` + `daas.md` regenerated. Find it later via `fd-daas-dashboard`."

## Step 7 - Write the dashboard instruction md

- **Standalone**: `daas-doc/dashboard/<slug>-dashboard.md` (create `daas-doc/dashboard/` on first use).
- Content: `# <Name>` + slug, introduction, `file://` URL, entity coverage + time range, source tables + columns, refresh cadence, a one-line "how to refresh" note (manual re-run of fetch+upsert).

## Gotchas

- **ECharts is the constraint; vendor it locally.** New dashboards MUST load ECharts from `dashboards/vendor/echarts.min.js` (relative). No CDN `<script>` (silent failure behind proxies), no CSS-only bar divs.
- **Entity + time filters are mandatory.** Bake data as JSON + wire a `<select>` (entities) + date inputs (time range) that re-render via `chart.setOption`. A single-entity dashboard still has the `<select>` (one option).
- **Validate before you bake.** Step 3 exists because a dashboard with a missing entity or empty time range looks fine but lies. Always fetch + check coverage first; abort on empty.
- **Registration lives in the DB, not the files.** `index.html` + `daas.md` are regenerated from `dashboards` by `register_dashboard.py` - never hand-edit them. Rollback = `register_dashboard.py delete --slug <slug>` + `rm dashboards/<slug>.html` + removing the companion md.
- **`chart_config` is structural** (`[{type, source_table, x, y, filterable}]`), not a full ECharts option blob - keeps the DB row small.
- **Dashboard HTML home** is repo-root `dashboards/` (configurable via `DASHBOARDS_DIR`). Older dashboards may still be at `fd-daas-mcp/dashboard-mcp/dashboards/` - move them to `dashboards/` and repoint `file_path`/`file_url` via `register_dashboard.py update` when migrating.
- To open or find an existing dashboard, use `fd-daas-dashboard`.
